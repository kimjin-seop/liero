# 리에로 포에버 — 서버 배포 가이드

배포 주소: **https://liero.oddplay.kr/**

## 구성

```
liero-forever/
├── server.js                  게임 서버 (웹페이지 제공 + 실시간 대전)
├── public/index.html          게임 화면 (클라이언트 전체가 이 파일 하나)
├── package.json / package-lock.json
├── Dockerfile                 도커로 배포할 때
└── deploy/
    ├── nginx-liero.oddplay.kr.conf   nginx 설정 (HTTPS + WebSocket)
    └── ecosystem.config.js           pm2 설정
```

- 서버가 게임 계산을 직접 합니다. 방장 탭이 내려가도 게임이 멈추지 않고, 조작 치트도 막힙니다.
- 게임 규칙 코드는 `public/index.html` 안의 `//CORE-START ~ //CORE-END` 부분 하나뿐입니다. 서버가 시작할 때 이 부분을 읽어서 씁니다. 그래서 **무기 수치나 물리를 바꿀 때 index.html만 고치고 서버를 재시작**하면 클라이언트와 서버에 함께 반영됩니다.
- 같은 index.html을 claude.ai 아티팩트에 올려도 동작합니다. 서버에서 열면 서버 모드, claude.ai에서 열면 기존 공유 방식으로 자동 전환됩니다.
- 필요한 것: Node.js 18 이상 (20 권장). 외부 패키지는 `ws` 하나뿐입니다.

## 1. 내 PC에서 먼저 실행해 보기

```bash
cd liero-forever
npm install
npm start
```

브라우저에서 http://localhost:3000 을 엽니다. 창을 두 개 띄워 온라인 대전 → 방 만들기 → 다른 창에서 입장 → 둘 다 준비를 누르면 게임이 시작됩니다.

## 2. 리눅스 서버(VPS)에 배포 — 추천

Ubuntu 22.04/24.04 기준입니다. 한국 사용자가 대상이면 **서울 리전** 서버를 쓰세요. 실시간 게임이라 핑이 체감에 바로 영향을 줍니다. 예: AWS Lightsail 서울, 오라클 클라우드 춘천/서울(무료 티어), 네이버 클라우드, Vultr 서울.

### 2-1. DNS 연결

도메인 관리 화면(oddplay.kr)에서 레코드를 하나 추가합니다.

| 타입 | 이름 | 값 |
|---|---|---|
| A | `liero` | 서버 공인 IP |

`ping liero.oddplay.kr` 로 서버 IP가 나오면 연결된 것입니다. 반영까지 몇 분에서 몇 시간 걸릴 수 있어요.

### 2-2. 서버 준비

```bash
# Node.js 20 설치
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt-get install -y nodejs nginx

# pm2 (프로세스 관리: 꺼지면 자동 재시작, 재부팅 시 자동 실행)
sudo npm install -g pm2

# 방화벽 (ufw를 쓰는 경우)
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
```

> 클라우드 콘솔의 보안 그룹(방화벽)에서도 **80, 443 포트**를 열어야 합니다. 3000번은 열지 마세요. nginx만 외부에 노출합니다.

### 2-3. 게임 서버 올리기

```bash
# 내 PC에서 서버로 파일 복사 (예시)
scp -r liero-forever ubuntu@서버IP:~/

# 서버에서
cd ~/liero-forever
npm ci --omit=dev
pm2 start deploy/ecosystem.config.js
pm2 save
pm2 startup        # 출력되는 sudo 명령을 한 번 복사해서 실행
```

`curl http://127.0.0.1:3000/healthz` 에서 `{"ok":true,...}` 가 나오면 정상입니다.

### 2-4. nginx + HTTPS

```bash
sudo cp deploy/nginx-liero.oddplay.kr.conf /etc/nginx/sites-available/liero.oddplay.kr
sudo ln -s /etc/nginx/sites-available/liero.oddplay.kr /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 무료 HTTPS 인증서 (Let's Encrypt)
sudo apt-get install -y certbot python3-certbot-nginx
sudo certbot --nginx -d liero.oddplay.kr
```

이제 https://liero.oddplay.kr/ 로 접속됩니다. 인증서는 certbot이 자동으로 갱신합니다.

> nginx 설정의 `/ws` 부분이 WebSocket 연결을 넘겨주는 핵심입니다. 이게 빠지면 페이지는 뜨는데 "게임 서버에 연결할 수 없어요"가 나옵니다.

### 2-5. 업데이트할 때

```bash
cd ~/liero-forever
# 바뀐 public/index.html 또는 server.js 를 덮어쓴 뒤
pm2 restart liero-forever
```

재시작하면 진행 중인 방은 초기화됩니다. 사람이 적은 시간에 하세요.

### 자주 쓰는 명령

```bash
pm2 logs liero-forever     # 로그 보기 (게임 시작/방 닫힘 기록)
pm2 status                 # 상태 확인
pm2 restart liero-forever  # 재시작
```

## 3. 도커로 배포 (선택)

```bash
docker build -t liero-forever .
docker run -d --name liero --restart unless-stopped -p 127.0.0.1:3000:3000 liero-forever
```

nginx와 HTTPS는 2-4와 똑같이 설정합니다.

## 4. 클라우드 플랫폼 (Render / Railway / Fly.io)

서버 관리가 귀찮다면 이쪽도 됩니다. WebSocket을 지원하는 곳이어야 합니다.

- **Render:** New → Web Service → 이 폴더를 올린 GitHub 저장소 선택 → Build `npm ci`, Start `npm start` → Settings → Custom Domain에 `liero.oddplay.kr` 추가 후 안내된 CNAME을 DNS에 등록. 무료 플랜은 15분간 접속이 없으면 잠들어 첫 접속이 30초쯤 느립니다.
- **Railway / Fly.io:** Dockerfile을 자동 인식합니다. 커스텀 도메인을 연결하고 DNS에 CNAME을 추가하세요. Fly.io는 도쿄(nrt) 리전이 한국과 가깝습니다.

> 인스턴스는 **반드시 1개**로 두세요. 방 정보를 서버 메모리에 두기 때문에, 여러 대로 나누면 서로 다른 방 목록이 보입니다.

## 5. 설정값 (환경 변수)

| 변수 | 기본값 | 설명 |
|---|---|---|
| `PORT` | 3000 | 서버 포트 |
| `HOST` | 0.0.0.0 | 바인딩 주소 (nginx 뒤라면 127.0.0.1 권장) |
| `MAX_CLIENTS` | 300 | 동시 접속 최대 인원 |
| `MAX_ROOMS` | 60 | 최대 방 개수 |

## 5-1. 온라인 방에 봇 섞기

방장은 대기실에서 `add_bot` / `remove_bot` 메시지로 봇을 넣고 뺄 수 있습니다(게임 중에는 불가). 사람+봇 합쳐 최대 6명이고 봇은 최대 5명이며, 봇은 항상 준비 완료 상태입니다. 방장 혼자여도 봇이 1명 이상이면 시작할 수 있고, 봇 입력은 서버가 매 틱 `Bot.think`로 직접 만들어 사람 입력과 함께 시뮬레이션합니다(클라이언트가 봇 입력을 보낼 수 없습니다). 게임이 끝나 대기실로 돌아와도 봇은 유지되고, 방에 사람이 한 명도 없으면 방은 닫힙니다.

### 봇 AI (원작에 없는 자체 구현, CORE 의 `Bot`)

- 목표: 가까운 상대 우선. 사이에 바위가 있거나 한동안 진전이 없던 상대는 뒤로 미룹니다.
- 이동: 흙은 조준 방향으로 파고 가고, 바위가 가로막으면 8px 격자 길 찾기로 돌아갑니다. 위·아래로 가파르면 좌우로 번갈아 파며 오르내리고, 머리 위가 비면 점프·로프를 씁니다. 걷다가 막히면 조준을 위아래로 쓸면서 앞을 팝니다.
- 정지 방지: ① 4초(`BOT_STALL`) 동안 30px 도 못 움직이거나 ② 10초(`BOT_LONG`) 동안 피해도 못 주고 다가가지도 못하면 그 목표를 미루고 다른 방향으로 빠져나갑니다(연속이면 더 오래). ③ 상대가 안 보이는 채 바위 틈에서 막힌 시간이 10초(`BOT_JAM`) 쌓이면 무기를 가리지 않고 쏩니다(마지막 수단).
- 자폭 방지: 무기마다 안전 거리(`botSafe`: 폭발 범위 + 파편·자탄)를 계산해 상대나 바로 앞 벽이 그보다 가까우면 쏘지 않고 다른 무기로 바꿉니다. 곧 터질 폭탄 옆에서는 물러납니다. 봇 무기 구성(`botLo`)에서 설치형(지뢰류·스파이크볼)과 짐은 빼고, 가까이서 써도 안전한 무기를 하나는 넣습니다.
- 측정(봇 4명 15분 × 8판 가속 시뮬레이션, 수정 전 → 후): 판이 멈춘 경우 8 → 0판, 분당 킬 0.29 → 7.6, 자폭 비율 16.7% → 7.6%.
- 추적 모드(`BOT_HUNT` 1200틱 = 20초, `BOT_HUNT_MAX` 2700틱, `BOT_NEAR` 90px, `BOT_BUSY` 300틱 = 5초): 목표 하나를 고정하고 기존 이동(파기·로프)으로 다가갑니다. 시작 조건은 ① 그 봇이 20초 동안 피해를 주지도 받지도 않았을 때(가장 가까운 사람, 사람 정보가 없으면 가장 가까운 상대) ② 어떤 사람이 20초 동안 혼자 있을 때(피해를 안 받고 90px 안에 아무도 없음) 그 사람과 가장 가까운 봇 하나(그 봇이 최근 5초 안에 피해를 주거나 받았으면 교전이 끝날 때까지 미룸: 싸우던 봇을 빼내 봇끼리 교전이 줄어드는 것 방지). 목표에게 피해를 주거나 목표가 죽거나 길이 없거나 45초가 지나면 끝납니다. 사람 지렁이 번호는 부르는 쪽이 `bot.hum` 에 넣습니다(서버 `Room.start`, 클라이언트 연습 모드). 원작 규칙·물리는 그대로입니다.
  - 측정(가만히 있는 지렁이 1 + 봇 3, 지형 12개 × 3분, 고정 난수): 봇이 80px 안에 처음 오는 시간 평균 39.0 → 23.5초, 최장 150.9 → 59.7초, 중앙값 21.4초 그대로. 위아래로 멀리 떨어진 경우는 오르내리는 데 시간이 걸려 여전히 40초 이상 걸릴 수 있습니다.
  - 봇끼리 교전(같은 구성, 지형 8개 × 3분): 봇간 킬 분당 3.33(추적 없음) → 2.71. 줄어든 몫은 봇이 사람 쪽으로 가는 시간(사람 사망 분당 0.63 → 0.92)이며, 추적 조건 ①만 켜도 2.96 입니다. 지형마다 편차가 ±0.2 정도 있습니다.
  - 알려진 한계(기록): 여러 봇이 동시에 ①로 같은 사람에게 몰릴 수 있습니다.

### 게임 중 퇴장·색 중복

- 게임 중 나간 사람의 지렁이는 서버가 바로 판에서 뺍니다(`Sim.drop`, 점수 변동 없음). 스냅샷 `gn`(비트마스크)으로 전달되고 남은 사람 화면에 알림이 뜹니다. 남은 참가자(봇 포함)가 1명 이하면 승자 없이 판을 끝내고 대기방으로 돌아갑니다. 나간 자리는 `pl` 에서 `null` 로 비워, 같은 판에 다시 들어와도 관전자가 됩니다. 나간 사람이 남긴 탄·지뢰로는 킬·승리가 오르지 않고 맞은 쪽 데스만 기록됩니다.
- 같은 방에서 색이 겹치면 서버가 나중에 고른 사람에게 안 쓰는 색을 줍니다.
- 게임 중인 방에도 들어갈 수 있습니다(관전). 정원 6명은 참가자(사람+봇) 기준이고 관전자는 방마다 8명(`MAX_SPECT`)까지입니다. 관전자의 입력은 쓰이지 않으며, 판이 끝나면 대기방에 남아 다음 판부터 입장 순서대로 참가합니다(대기방 인원이 6명을 넘으면 넘는 사람은 다음 판도 관전). 방 목록의 게임 중인 방 인원(`total`·`humans`)은 참가자 기준이고 관전자 수는 `spec`/`smax` 로 따로 옵니다.

### 화면 표시(원작에 없는 편의 기능, 규칙·수치와 무관)

- 화면 밖 상대: 화면 가장자리에 상대 색 화살표와 이름 머리글자(봇은 '봇 ' 뒤 첫 글자)를 가까운 순으로 3명까지 표시합니다. 점수판·체력판·버튼·채팅창 밑이면 화면 안쪽으로 당겨 그립니다. 관전 화면에도 나옵니다.
- 모바일 가로: 버튼 4개는 화면 좌우 끝(왼쪽 점프·놓기/파기, 오른쪽 무기/로프, 위에서 150px 아래)에 세로로 놓이고, 체력판은 상단 버튼 줄 오른쪽의 150×36 크기입니다. 모바일 세로의 버튼 줄은 왼쪽부터 파기·로프·무기·점프·놓기입니다. 파기를 왼손 쪽에 둔 것은 오른손 엄지로 조준·발사하면서 팔 수 있게 하기 위해서입니다.
- 모바일 대기방: 카드가 화면 높이 안에 들어가고 플레이어·옵션·무기 영역만 안에서 스크롤됩니다(준비/시작 버튼이 항상 보임). 가로에서는 왼쪽 목록·오른쪽 채팅+버튼의 2단입니다. 이 가로 압축 레이아웃의 조건은 '화면 높이 560px 이하이면서 가로 방향'(`max-height:560px` + `orientation:landscape`)뿐이고, 폭이나 포인터(터치 여부) 조건은 없습니다. 그래서 창을 낮게 줄인 데스크톱에서도 같은 배치가 됩니다.
- 온라인 결과 화면: '다시 하기'(대기방으로 돌아가는 즉시 준비 상태가 됨, 다시 누르면 취소)와 '나가기' 버튼이 있고, 6초 뒤 대기방 자동 복귀는 그대로입니다. 혼자+봇 방에서 '다시 하기'를 누르면 대기방 복귀 즉시 새 판이 시작됩니다(봇은 항상 준비 상태라 방장 준비 = 시작 규칙 그대로). 결과 화면이 뜬 뒤 0.7초(`RES_GUARD_MS`, 자체 값) 동안은 결과 버튼 클릭을 받지 않습니다(마지막 킬 순간의 발사 연타로 '나가기'가 눌리는 것 방지, 화면 표시 없음. 연습·2인 모드의 '다시 하기'·'메뉴로'도 같음).
- 낮은 가로 화면(모바일 가로): 높이 500px 이하 가로에서는 결과 카드를 줄여 6명도 스크롤 없이 제목·버튼이 보입니다(넘치면 목록만 스크롤). 가로 대기방에서 키보드가 올라와 보이는 높이가 280px 이하가 되면 제목 줄·상태 줄을 접고 버튼을 줄여 채팅 입력칸이 버튼에 가려지지 않습니다(`#s-lobby` 컨테이너 쿼리, 미지원 브라우저는 이전 모양).
- 무기 선택: 무기 칸을 누르면 목록이 팝업으로 뜹니다(바깥·✕·Esc 로 닫음). 목록은 분류 배지(총/폭발/투척/설치/광선/분사/도구) 순서이고, 분류는 `index.html` 의 `WCAT`(표시 전용)에서 고칩니다.
- 관전: 아래 가운데에 따라가는 지렁이 이름이 나오고, ←/→(또는 A/D) 키나 화면 왼쪽/오른쪽 절반 탭으로 대상을 바꿉니다(고르지 않으면 킬이 가장 많은 지렁이). 채팅 입력 중의 첫 클릭은 입력 포커스만 풀고 대상은 바꾸지 않습니다. 관전 중에는 키 안내와 터치 조작판을 숨깁니다. 방 목록에서 게임 중인 방의 버튼은 '관전' 이고, 결과 화면에는 나간 사람 옆에 '나감' 이 붙습니다.
- 상단 나가기·전체화면 버튼은 반투명이고, 지렁이나 이름표가 그 밑에 오면 더 흐려집니다(마우스를 올리면 다시 또렷해지며, 터치 기기에서는 탭 뒤에도 흐림이 유지됩니다). 알려진 한계(기록): 모바일 가로 체력판의 가로 위치는 고정값입니다.
- 슬로모션 중에는 화면 가장자리에 푸른 테두리가 맥동합니다(폭발이 화면 밖이어도 이유를 알 수 있게).

## 5-2. 원작 기준 무기·물리 (Liero 1.33)

무기·폭발·파편 수치와 지렁이 물리는 원작 `LIERO.EXE` 에서 추출한 자료(`analysis/orig_data/*.json`, 정리 문서 `analysis/original_weapons_spec.md`)를 기준으로 합니다. 무기 표(`WEAPON_RAW`·`NOBJ_RAW`·`SOBJ`)는 원시값 그대로이고, CORE 의 `mkDef` 가 원작 70프레임/초를 서버 60틱으로 환산합니다(속도 ×7/6, 가속 ×(7/6)², 시간 ×6/7).

- 무기: 원작 40종 + 자체 무기 1종(텔레포트 건). 플레이어마다 5개를 골라 들고 나갑니다(메뉴·대기방의 "무기" 칸, `{t:'rp', p:{lo:[무기 번호 5개]}}`). 재장전은 들고 있는 무기만 진행됩니다.
- 폭발: 원형이 아니라 정사각형 범위에서 축별 선형 감쇠(큰 폭발 최대 15). 큰 피해는 파편·자탄에서 나옵니다. 지형은 지름 15/11/7/9/5px 에 해당하는 원으로 깎습니다.
- 레이저: 탄창 80, 틱마다 1발·피해 1, 지형·맵 경계·지렁이에 닿을 때까지 직진(사거리 제한 없음), 닿은 흙을 지름 5px 로 뚫습니다.
- 미사일: 날아가는 동안 좌우 키로 방향을 돌리고 위(또는 로프 감기) 키로 가속합니다. 그동안 지렁이는 걷지 못합니다.
- 빅 누크: 갈라지는 순간 서버 시뮬레이션이 `NUKE_SLOW`(150)틱 동안 1/`SLOW_DIV`(3) 속도로 진행됩니다(스냅샷 `sl`). 클라이언트는 스냅샷을 그대로 따릅니다.
- 보너스 상자: 무작위로 떨어지는 체력(10~60 회복)·무기(고른 무기 즉시 장전) 상자. 부비 트랩은 상자와 같은 형식(`[21,x,y,종류]`)으로 전송돼 구분할 수 없습니다.
- 방 옵션 "재장전 시간 0"(`rl0`, 기본 끔, 방장 값 적용): `{t:'rp', p:{rl0:true}}`. 대기실 `g.rl0`(bool), 게임 중 `g.r0`(1/0).
- 지렁이: 중력·걷기·마찰·점프·벽 반사·조준 가속·리스폰 대기를 원작 상수로 맞췄습니다. 몸 판정은 반지름 약 3.2px 의 속 찬 원판(37점)입니다(원작은 다음 위치의 좌우 열 7점(x±1)·상하 행 3점(y±4)을 세어 2점 미만이면 지나가는 방식이라 판정 모양은 다릅니다. 알려진 차이: 원작은 진행 방향 반응점이 1점만 닿아도 그 축 속도를 0 또는 -1/3 반발로 만들어, 로프에 벽 쪽으로 끌리면 벽에 붙어 멈추고 몸 옆의 1px 에도 걷기가 막힙니다. 웹판은 벽을 타고 끌려 올라가지만 원판 가장자리에 닿는 1px 턱에서는 멈춥니다. 2026-11-18 측정과 원작 방식 변형 파일은 `_backup/playtest_fix_orig_collision_variant/` 참고). 파기는 좌+우 동시(또는 파기 키)를 누를 때마다 1회, 조준 방향 앞에 지름 7px 구멍 두 개를 내며 몸을 밀어 주지 않습니다. 누르고 있어도 반복되지 않으니 연타합니다(원작과 같음, 봇은 `BOT_DIG` 9틱마다 누름). 입력 프로토콜: 파기 키는 눌림 비트(`in` 의 64)와 함께 누름 횟수 `dg`(로프 `rp`·무기 전환 `sw` 와 같은 카운터, `{t:'rp', p:{in, dg}}`)를 보냅니다. 서버는 비트의 올림 에지나 `dg` 값 변화 중 하나라도 있으면 그 틱에 1회 팝니다(같은 틱에 둘 다 와도 1회). 그래서 서버 틱(16.7ms)보다 짧은 탭이나 슬로모션으로 건너뛴 틱의 탭도 사라지지 않습니다. `dg` 를 보내지 않는 예전 클라이언트는 비트만으로 전과 같이 동작합니다.
- 킬 집계: 다른 지렁이에게 죽었을 때만 가해자 킬 +1 입니다. 자폭이나 가해자 없는 사망은 데스만 오르고 킬은 변하지 않습니다(원작과 같음, OpenLiero worm.cpp 448~451행). "먼저 k킬 달성 시 승리"는 웹 자체 규칙입니다.
- 닌자 로프: 갈고리 속도 4px/프레임, 날아가다 250px 보다 멀어지면 사라지지 않고 지렁이 쪽으로 당겨져 돌아오며, 붙는 순간 줄 길이 28px 이 되어 끌려가고, 줄보다 멀면 갈고리 쪽으로 일정한 가속을 받습니다(진자 고정이 아님). 상대에게 걸리면(`rs=3`) 양쪽이 같은 힘으로 끌립니다. 방 옵션 `pull`(기본 켬)을 끄면 로프가 상대를 통과합니다(`g.pull` / `g.pu`). 줄 길이는 갈고리가 날아가는 중에도 바뀝니다(원작과 같음, 서버는 감기 `in` 128·풀기 `in` 256 비트를 날아가는 중에도 적용). 다만 입력 경로는 기기마다 다릅니다. 데스크톱: 날아가는 중에는 감기(W, 2인 모드 Q/L)만 되고, 풀기는 파기 키(S/Shift)와 같은 키라 붙은 뒤에만 됩니다(날아가는 중에는 파기). 줄은 최대 길이로 나가므로 날아가는 중 풀기는 먼저 감았을 때만 의미가 있습니다. 모바일: 갈고리가 나가 있는 동안(날아가는 중 포함, 스냅샷 `rs` 1~3) 왼쪽 스틱 위 = 감기, 아래 = 풀기이며 점프로 처리하지 않습니다(`stickBits`). 로프 버튼을 누른 뒤 250ms(`ROPE_HINT_MS`, 자체 값) 동안은 스냅샷 반영 전이라도 나가 있는 것으로 봅니다. 예전에는 붙은 뒤(`rs` 2·3)에만 켜져서 날아가는 중 스틱 위가 점프로 전송되어 갈고리가 취소됐습니다. 점프(버튼·키)는 원작대로 날아가는 중에도 로프를 놓습니다(OpenLiero worm.cpp 1119~1125행). 프로토콜 변경은 없습니다(클라이언트 입력 매핑만 변경). 검토 후 보류한 제3안: 로프에 끌려가다 1px 턱에 걸릴 때 '세로로 막히면 옆으로 비켜 주는' 처리는 원작에 없는 자체 규칙이라 채택하지 않았고, 턱 걸림은 현행대로 둡니다.

## 5-3. 스냅샷 형식과 예산

스냅샷 한 개는 3700바이트 이내입니다(`SNAP_MAX`). 싣는 순서는 ① 직전 스냅샷 이후의 지형 연산(빠지면 지형이 어긋나므로 항상) ② 발사체(우선순위 → 지렁이와 가까운 순) ③ 남는 자리에 지난 지형 연산 재전송(최대 60개)입니다.

- `p`: 부가 정보가 있는 발사체 — 레이저 `[4,x,y,x2,y2]`, 아이템·부비 트랩 `[21,x,y,종류]`
- `q`: 나머지를 종류별로 묶은 납작한 배열 `[t,n,x,y,x,y,...]` (발사체 1개당 약 8바이트)
- 상한: 발사체 총 `PROJ_MAX`(420)개, 틱당 폭발 `BOOM_TICK`(12)회(넘치면 다음 틱으로 미룸), 한 번에 뿌리는 파편 `SPL_MAX`(60)개
- `SNAP_MAX` 는 `g` 본문 기준입니다. 전용 서버에서는 `{"t":"g","g":...}` 로 감싸 약 13바이트가 더 붙습니다(실측 최대 3713바이트). 서버 → 클라이언트 웹소켓 전송에는 크기 제한이 없고(`maxPayload` 16KB 는 서버가 받는 쪽에만 적용), 그 값보다도 작습니다.
- 슬로모션 중에는 시뮬레이션이 3틱에 1번만 진행하므로 서버도 진행한 틱에만 스냅샷을 보냅니다(평소 2틱에 1번). 클라이언트는 직전 장면과 현재 장면 사이를 프레임마다 이어 그립니다(표시 전용 보간: 화면 갱신 간격 중앙값 50ms → 16.7ms).
- `kf`: 최근 킬 기록 4건 `[일련번호, 죽은 지렁이, 죽인 지렁이(-1 없음), 무기 번호(-1 없음)]`. 부활 대기 화면의 '누가 · 무엇으로' 표시에 씁니다. `gn`: 나간 참가자 비트마스크.

### 보호 장치(원작에 없는 제한)

무기 수치와 규칙은 원작 그대로이고, 서버 권위·다인 환경에서 한 사람이 방 전체를 망가뜨리지 못하게 하는 최소한의 제한만 따로 둡니다. 코드 주석에 `보호 장치(원작 외)` 로 표시되어 있습니다.

| 상수 | 값 | 내용 |
|------|----|------|
| `RL0_GAP` | 10프레임 | 재장전 0 옵션에서 탄창 1·delay 0 무기(수류탄·지뢰·빅 누크·라이플 등)의 최소 발사 간격. 원작은 매 프레임 발사 |
| `INST_MAX` | 24개 | 소유자당 설치물(지뢰류·스파이크볼·부비 트랩) 수. 넘치면 그 소유자의 오래된 것부터 사라짐 |
| 소유자별 몫 | `PROJ_MAX` ÷ 참가자 | 총 상한을 넘으면 자기 몫을 넘긴 소유자의 것만 버림(우선순위 낮은 것 → 같은 등급에서는 새것부터). 남의 탄은 밀려나지 않음 |
| `OWN_IMM` | 6틱 | 발사한 무기 본체가 발사자에게 맞지 않는 시간. 파편·자탄에는 없음(원작처럼 자기 것에도 맞음) |
| `SLOW_CD` | 540틱 | 슬로모션이 끝난 뒤 다시 걸리기까지의 시간 |
| `SPAWN_ROCK` | 9px | 리스폰 자리와 바위 사이 최소 여유. 바위 틈에 끼어 태어나 못 움직이는 일 방지(그런 자리뿐이면 그대로 씀) |
| 폭발 대기열 | `BOOM_Q` 300 | 가득 차면 피해가 작은 대기 폭발부터 밀려나고, 버린 수는 판이 끝날 때 서버 로그에 남음 |

발사 간격은 원작 프레임 단위 그대로입니다(delay d → d 프레임 주기, 0 과 1 은 매 프레임 = 70발/초). 60틱 서버에서는 한 틱이 70/60 프레임이라 매 프레임 무기는 6틱에 한 번 한 틱 2발이 나갑니다. 간격은 무기별로 따로 흐르고(원작 `delayLeft`), 고른 무기 5개 모두 들고 있지 않아도 매 틱 줄어듭니다. 무기를 바꾸는 것 자체에는 발사 지연이 없습니다(예전의 전환 후 3프레임 지연은 원작에 없는 값이라 뺐습니다).

방장은 입장 순서(서버가 입장 시각으로 정함)가 가장 빠른 사람입니다. 클라이언트가 보내는 `t0` 는 전용 서버에서 쓰이지 않습니다.

## 5-4. 테스트

`npm test` (`node --test`). `test/weapons.test.js` 는 CORE 구간을 서버와 같은 방식으로 불러와 무기 표가 추출 자료와 같은지, 무기별 핵심 동작, 스냅샷 예산, 물리 상수, 재장전 0 다인 연사(상한·슬로모션 보호 장치)를 확인합니다. `test/server.test.js` 는 서버를 임시 포트로 띄워 방장 판정과 방 옵션(`rl0`)·무기 선택(`lo`) 반영, 색 중복 재배정, 게임 중 퇴장 처리를 확인합니다. 봇끼리 두어도 멈추지 않는지는 `test/weapons.test.js` 의 봇 테스트(고정 난수, 지형 2개 × 5분)가 확인하고, 추적 모드 목표 고정은 같은 파일의 '봇 추적 모드' 테스트가 확인합니다.

## 6. 성능 참고

- 방 하나는 60틱으로 돌아가고, 플레이어마다 초당 30번 상태를 받습니다. 6명 방 기준 사용자당 대략 초당 30~70KB입니다.
- 1코어 1GB 서버로 동시에 방 10~20개 정도는 여유 있게 돌아갑니다.
- 트래픽이 많아지면 nginx에서 gzip 대신 WebSocket 압축(permessage-deflate)을 켜는 것보다, 먼저 서울 리전의 더 좋은 CPU로 옮기는 게 효과가 큽니다.

## 7. 문제 해결

| 증상 | 확인할 것 |
|---|---|
| 페이지가 안 열림 | DNS A 레코드, 클라우드 방화벽 80/443, `sudo nginx -t` |
| 페이지는 열리는데 "게임 서버에 연결할 수 없어요" | nginx `/ws` 설정, `pm2 status`로 서버 실행 여부 |
| 게임 중 자꾸 끊김 | nginx `proxy_read_timeout`, 클라우드 로드밸런서의 유휴 타임아웃(60초 이상) |
| 수정한 게 반영 안 됨 | `pm2 restart liero-forever` 후 브라우저 강력 새로고침 |
